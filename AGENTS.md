## Project rules

- Sales-document compositions, items and outputs are read by staff; social assets and metrics are read by staff or through their RLS-visible parent post, so child rows cannot expose another artist's hidden post. Preserve existing write policies when tightening reads.

- User account deletion is a BIG C-only server action that revalidates the exact email before deletion, preventing accidental or client-forged removals.- Roster occupancy is computed by the SQL function `roster_occupancy_months` (productions/phases/assignments, billing sprints, open pitches/candidacies); UI and the weekly `notify_roster_income_gaps` cron share it so alerts and screens never disagree.
- Agency work for an artist is aggregated at read time (`fetchAgencyTimeline`) from pitches, candidacies, productions, press and the manual `composer_activity_log`; never duplicate those sources into the log.
- AI-read contract payment terms are only suggestions; they become `production_billing_sprints` only after explicit human confirmation and never overwrite existing sprints.
- Gantt colour belongs to the production (`productions.gantt_color`, 25-key palette in `src/lib/project-palette.ts`), not to the phase type; one row per phase under its film so every film reads as one colour block.
- Task notifications (`notify_task_assignment`) run as an AFTER trigger on `actions`; never move them to BEFORE INSERT — the notification FK to `actions` cannot see the not-yet-inserted row and task creation with an assignee fails. Row mutations (assignment status defaults) stay in the BEFORE trigger `actions_assignment_defaults`.
- Onboarding content lives in `onboarding_slides` (staff read, BIG C write) with per-user `onboarding_progress`; seeded media are CDN assets, BIG C uploads go to the private `onboarding-media` bucket and are shown via signed URLs. Slides are rendered from `layout` + a light text markup (`##`, `-`, `>`, `@`, `**`) in `slide-layouts.tsx`, never from screenshots of the original deck, so BIG C can edit text and keep the app's design.
- Style tagging has two levels that must stay separate: composer-level styles in `composer_styles`, and track-level tags on the demo itself — `composer_demos.style_tags` (free-text array for mood, texture, tempo, tonality, use) plus `composer_demo_styles` linking a demo to `music_styles`. A track's tags must never be promoted into roster filters.
